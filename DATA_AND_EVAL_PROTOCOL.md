# Data and Evaluation Protocol

**Project:** Evidence-Grounded Document Intelligence

**Protocol version:** 1.0

**Frozen on:** 2026-08-27

**Primary data:** DocScope

**Fallback data:** MMLongBench-Doc-V2

## 1. Purpose

This protocol prevents the project from becoming a sequence of untracked prompt and architecture changes. It defines the data boundary, split policy, evaluation units, Oracle Evidence experiment, failure attribution rules, cost logging, contamination controls, and decision gates before system code is written.

Any later change that can affect results must be recorded with:

- change date and rationale;
- affected experiments;
- whether prior results were rerun;
- whether the change used tuning, calibration, or locked test information.

## 5. Split policy

### 5.1 Locked official test

The 730 official test questions are locked. They may not be used for:

- prompt development;
- chunk-size or top-K selection;
- model selection;
- threshold calibration;
- failure-driven architecture choices;
- manual correction of the pipeline.

Run the full test only after the model, prompt, retrieval configuration, thresholds, and evaluator are frozen. A failed infrastructure run may be resumed, but its partial scores cannot influence changes.

### 5.2 Clean development pool

Remove from official dev every question whose document appears in official test. The audited clean pool is:

- 388 questions;
- 117 documents;
- zero document overlap with locked test.

Split this clean pool by **document ID**, never by question:

- approximately 70% of documents for `development_tune`;
- approximately 30% of documents for `development_calibration`;
- random seed `20260827`;
- greedy stratification targets: answerability, `extract_class`, evidence modality, and single-page versus multi-page evidence.

The exact generated counts and document IDs must be committed as a manifest before modelling begins. If perfect stratification is impossible, preserve document isolation and report the imbalance.

### 5.3 No benchmark fine-tuning by default

V1 uses off-the-shelf retrievers and reasoning models. If failure analysis later justifies training a reranker, it may use only `development_tune`; `development_calibration` and locked test remain untouched. This change requires a protocol amendment.

## 6. Canonical retrieval unit and document representation

The canonical evaluation unit is a **PDF page** because DocScope’s primary evidence labels are page IDs and bboxes.

Minimal representation:

1. preserve original PDF and page numbering;
2. extract text blocks with a fixed parser version;
3. retain `doc_id`, page index, block coordinates when available, text, and extraction status;
4. create chunks within page boundaries only;
5. retrieve chunks, then aggregate scores to pages;
6. preserve a reversible mapping from every retrieved chunk to its source page and coordinates.

No OCR fallback is applied silently. Pages with little/no extracted text receive a `text_layer_missing` flag and remain in modality-specific analysis.

Initial chunk parameters are tuned only on `development_tune`. The search range must be small and predeclared before running, for example 256/512 tokens with 0/64-token overlap. The project should prefer the simplest configuration that is not materially worse.

## 7. Baselines and change control

Mandatory initial baselines:

- **B0 Question-only control:** no document context; detects prior knowledge and possible contamination.
- **B1 BM25:** sparse lexical page/chunk retrieval.
- **B2 Dense:** one pinned, off-the-shelf embedding model.
- **B3 Long-context control:** entire document where technically feasible, evaluated on a predeclared development subset if full-document API cost is excessive.

Conditional components:

- **Hybrid:** only if BM25 and dense show complementary query-level successes.
- **Reranker:** only if candidate-set recall is high but ranking metrics/top-K completeness are poor.
- **Visual representation:** only if text-layer/visual-evidence failures are a major residual slice after basic retrieval is working.
- **Verifier model:** not part of the initial V1 architecture; add only if unsupported answers remain frequent and a verifier hypothesis is separately tested.

Every conditional component needs a one-page experiment record: observed failure, hypothesis, metric expected to move, budget, result, and keep/drop decision.

## 8. Retrieval metrics

Report per question and aggregate:

- **Any-evidence Recall@K:** at least one gold evidence page retrieved;
- **Complete-evidence Recall@K:** all gold evidence pages retrieved;
- **Evidence-page Recall@K, Precision@K, and F1;**
- **MRR:** reciprocal rank of the first gold page;
- **nDCG@K:** binary page relevance unless a graded relevance rule is explicitly introduced;
- latency per query, index size, and retrieval compute.

Primary K values: 1, 3, 5, and 10. Top-K used for the reasoning model is selected on `development_tune`, then frozen.

Unanswerable questions and the answerable zero-evidence anomaly are excluded from evidence-recall denominators and reported in separate reliability slices.

Always report both macro question averages and micro evidence-page totals. Complete-evidence Recall is the primary retrieval metric because 62.3% of questions require multiple evidence pages.

## 9. Answer and grounding metrics

### 9.1 Answer quality

- official semantic answer accuracy with a pinned judge;
- deterministic exact match / normalized numeric match where applicable;
- answer accuracy by answerability, evidence modality, evidence-page count, and extraction class;
- bootstrap 95% confidence intervals over questions, with a document-clustered bootstrap sensitivity analysis.

### 9.2 Grounding quality

- predicted citation page precision, recall, and F1;
- complete evidence-chain rate;
- official bbox coverage labels where region predictions are produced;
- official atomic-fact consistency;
- **grounded correctness:** answer correct **and** required evidence adequately covered/supported;
- **unsupported-answer rate:** answered but not supported by cited/retrieved evidence.

LLM-as-judge configuration must be pinned by provider, model/version, date, prompt hash, temperature, and retry policy. Manually double-score a stratified sample of at least 50 records to estimate judge agreement and document disagreements.

## 10. Core Oracle Evidence experiment

Oracle Evidence is a controlled ladder, not one vague condition.

| Condition | Context given to the same reasoning model | What it controls |
|---|---|---|
| **C0 Closed-book** | Question only | Prior knowledge / contamination baseline |
| **C1 Real Retrieval** | Top-K output from the frozen retriever | End-to-end system |
| **C2 Oracle Page** | Full human-annotated evidence pages | Removes page retrieval failure; retains localization, perception, and reasoning difficulty |
| **C3 Oracle Region — primary oracle** | Gold bbox crops plus any native text intersecting those boxes | Removes page and region retrieval failure; retains perception and answer reasoning |
| **C4 Oracle Fact — diagnostic ceiling** | Gold atomic fact descriptions, without the gold final answer | Removes retrieval and most perception difficulty; measures answer composition/reasoning ceiling |

Controls:

1. Use the same model snapshot, system prompt, answer format, temperature, and decoding limits across C0–C4.
2. Never provide `answer.answer_text` to the model.
3. C4 is reported separately because gold fact descriptions may make some questions nearly trivial; it is not presented as ordinary RAG performance.
4. For unanswerable questions, the oracle context is empty and the expected action is abstention. Report them separately from answerable decomposition.
5. Cache immutable model responses before scoring.

Primary contrasts:

- `C1 → C3`: recoverable loss associated with real evidence retrieval/localisation;
- `C3 → C4`: loss associated with perception/fact extraction;
- `C4 → 100%`: residual answer reasoning/instruction-following loss;
- `C0 → C1`: value added by document evidence over prior knowledge.

These gaps are descriptive upper-bound decompositions, not automatic causal claims. Alternative valid evidence and annotation incompleteness must be checked in manual audits.

## 11. Failure attribution matrix

For answerable questions, assign initial cells using complete gold-page coverage and answer correctness:

| | Answer correct | Answer incorrect |
|---|---|---|
| Complete evidence retrieved | Grounded success candidate | Downstream failure candidate |
| Incomplete evidence retrieved | Lucky-guess / alternative-evidence candidate | Retrieval-associated failure candidate |

Then refine with oracle results and manual evidence review:

- **Confirmed retrieval failure:** C1 incorrect, C3 correct, and no valid alternative evidence was retrieved.
- **Persistent downstream failure:** C1 and C3 incorrect despite adequate gold evidence presentation.
- **Perception/localisation failure:** C3 incorrect but C4 correct.
- **Residual reasoning failure:** C4 incorrect.
- **Unsupported correct answer:** final answer correct but cited/retrieved evidence does not support it.
- **Alternative-evidence success:** predicted evidence differs from gold but genuinely supports the answer.
- **Annotation issue:** gold evidence/answer is incomplete or inconsistent.
- **Unanswerable handling failure:** system answers when the benchmark expects abstention, or abstains on supported evidence.

Do not label every `retrieval incomplete + answer correct` case a lucky guess without manual support review.

Manual audit quotas on development data:

- at least 25 examples from each populated major failure cell;
- all zero-evidence anomalies;
- at least 25 disagreements between answer correctness and grounding correctness;
- a balanced sample across text, table, chart, and image evidence.

## 12. Selective answering protocol

The abstention policy may use only signals available at inference time, such as:

- top retrieval score and score margin;
- sparse/dense agreement;
- number and diversity of retrieved pages;
- answerability prediction;
- answer confidence or repeated-run agreement, if budget permits;
- grounding/verifier score only if that verifier has been separately validated.

Fit thresholds or a lightweight calibrator on `development_calibration` only. Report:

- coverage;
- selective risk (error rate among answered questions);
- grounded selective risk;
- risk–coverage curve and AURC (lower is better);
- accuracy and grounded accuracy at 100%, 90%, 80%, and 60% coverage;
- unanswerable false-answer rate;
- abstention rate on answerable questions.

Never use Oracle Evidence, gold evidence coverage, or gold answerability as an inference-time feature.

## 13. Slices required in every final table

- answerable versus unanswerable;
- single-page versus multi-page evidence;
- number of gold evidence pages: 1, 2, 3–5, 6+;
- evidence modality: text, table, chart, image/figure, mixed;
- text-layer available versus missing/low-text;
- extraction class, kept as released labels until verified;
- document length buckets;
- BM25-only success, dense-only success, both, neither;
- confidence/coverage bands.

Small slices must include sample size and confidence intervals; do not draw strong conclusions from tiny cells.

## 14. Contamination controls

DocScope’s questions and hierarchical annotations were released in 2026, which reduces but does not eliminate direct benchmark contamination. Its source PDFs came from CommonCrawl snapshots through 2025-08, so document content may have appeared in model pretraining.

Controls:

1. run C0 question-only performance and report it beside all document-grounded results;
2. record exact model snapshot and evaluation date;
3. do not train or fine-tune on DocScope questions, answers, facts, or test PDFs;
4. never include gold answer/facts in prompts except C4’s explicitly labelled gold facts;
5. keep locked test outputs immutable and hash them;
6. disclose that source-document familiarity can inflate closed-book and long-context performance;
7. treat unusually correct closed-book answers as a manual contamination-review slice, not as proof of contamination;
8. if the fallback is used, disclose its higher contamination risk because most questions originate from a public 2024 benchmark widely used in model evaluations.

## 15. API, compute, latency, and cost protocol

Retrieval-only BM25/dense evaluation should be runnable locally without paid APIs. DocScope data itself is about 205 MB before page rendering, extraction caches, and embeddings.

The official example response contains about 45k input tokens for one full-document question. That is not a measured dataset average, but it gives the correct order of magnitude:

- 100-question full-document pilot: roughly 4.5 million input tokens at that example rate;
- 394-question official dev: roughly 17.7 million;
- 730-question official test: roughly 32.9 million;
- all 1,124 questions: roughly 50.6 million.

Retrieved-context conditions should be far smaller. Actual spending must be estimated only after measuring a pilot’s token distribution against the chosen provider’s current price.

Execution gates:

1. **Smoke test:** 10 development questions, no conclusions.
2. **Pilot:** 50–100 stratified `development_tune` questions; measure tokens, latency, parser failures, and judge stability.
3. **Development run:** full clean development split only after a written budget estimate.
4. **Locked test:** once after all choices are frozen.

For every call, log:

- experiment ID and question ID;
- provider, model snapshot, endpoint mode, and date;
- input/output tokens, cached tokens, latency, retries, and status;
- estimated cost using a versioned pricing snapshot;
- prompt hash and context IDs;
- judge calls separately from answer-generation calls.

Official page scoring is deterministic and requires no LLM. Official bbox, fact, and answer scorers require model judges. Cache judge results and never silently switch judge models within a comparison.

No paid full-benchmark run starts without an explicit monetary cap recorded in the experiment configuration.

## 16. Statistical comparison rules

- Compare systems on identical question sets.
- Report absolute metric deltas and paired bootstrap 95% confidence intervals.
- Use document-clustered resampling as a robustness check because multiple questions can share a PDF.
- Correct for multiple exploratory slice comparisons or clearly label them exploratory.
- A component is retained only if it improves the predeclared target metric meaningfully and its cost/latency trade-off is acceptable; leaderboard movement alone is insufficient.
- Negative and null results remain in the experiment log.
